## 发现的问题

### 问题 1 — major：`fx` 完全没接进 `monthly_run.py`，永远不会自动跑

`monthly_run.TICKERS` 是 12 家，`CROSS` 是 2 页，`fee_rates()` 是特判的第 13 条路径。
**没有任何一条路径调用 `fetch/fx.py`**（`grep -n "fx" monthly_run.py` 无输出）。
这意味着：交付的 `series/fx.csv` 在 cron 下**永远停在 2026-07**，而
`build/notional.py` / `build/pools.py` 会拿着一张越来越旧的汇率表算定基名义额，
且 `fx_rate` 的缺月护栏会在下个月**让整个横截面页 FAIL**，届时排查方向会指向 pools
而不是「fx 根本没人调」。

补充：本批次的 `ice.py` / `enx.py` / `miax.py` / `pools.py` / `notional.py` 同样未接线
（git 里全是 `??`），所以这很可能是「批次未完工」而非遗漏 —— 但 fx 是这批的**公共底座**，
它不刷新，上面所有池都不对。

**修复指令**：在 `monthly_run.py` 里仿 `fee_rates()` 加一个 `fx()` 步骤：
`load('fetch/fx.py','fetch_fx').update(SERIES, CACHE)`，放在 `build_cross()` **之前**
（理由与 fee_rates 相同：fx 变了，读它的生成器必须在本轮重跑，否则页面要等下一轮）；
失败时把 `'fx'` 计入失败清单让总状态变 `PARTIAL`，不要吞掉。ECB 在数据月内就发完，
所以**不要给它套 `not_due` 那张 LAG 表的下载闸门**，每天跑即可。

### 问题 2 — major：某币种在源头尾部消失时，静默退回旧月份，不报错

实测：把 SEK 的 2026-06 起观测从源数据里删掉后，
`compute_monthly()` + `_validate()` **不抛任何异常**，`latest_month()` 静默返回
`2026-05`（原为 `2026-07`）。

根因：`_scope()` 对「10 币种发布日集合不完全一致」的月份一律 `continue` 跳过。
这个设计对**头部**是对的（BRL 2008 年前尚未纳入名单，那是事实不是故障），
docstring 也这么解释；但它**对尾部同样生效**，而尾部缺币种只可能是故障
（ECB 改版 / 某币种被移出参考汇率名单 / 响应被截断）。
`update()` 的首月护栏只守**头部**，守不住尾部。
结果是 README 护栏 2「缺列一律失败，绝不静默写 NaN」在这个方向上被绕过 ——
它确实没写 NaN，但它**静默地什么都不写**，而 fx 没有页面、没有红点，
这个故障在人肉发现之前不会有任何信号。这正是该模块自己警告的
「错得刚好看不出来」那一类。

**修复指令**：在 `_scope()` 之后加一道尾部一致性检查 ——
取 `newest = max(daily['USD'])[:7]` 的**前一个月** `prev = _prev_month(newest)`，
若 `prev` 不在 `scope` 里，抛 `FxFetchError`，消息里列出
「该月 USD 有 N 个发布日，而 <这些币种> 分别只有 M 个」。
头部的合法缺席不受影响（那些月份远早于 `prev`）。
可选加固：断言 10 个币种的**最新观测日**互相不差超过 3 个 TARGET2 日。

### 问题 3 — minor：与 ECB 月频序列的对账，描述的对象与实际验的对象不是一回事

docstring 写：

> USD / JPY / BRL 在 2018-11 至 2019-03 共 15 个月，**本模块重算值**与官方月频值
> 相对差 ≤ 3.2e-14

我按字面复现（本模块的 `fx_avg_jpyusd` / `fx_avg_brlusd` 对 `M.JPY.EUR` / `M.BRL.EUR`
换算出的美元交叉）得到的是 **最大 1.75e−04**，比声称值大 10 个数量级，
一度让我以为解析错了。

查清了：ECB **不发布** USD/JPY、USD/BRL 的月频交叉序列，能对的只有各币种
**对欧元那一条腿**。我改按「原始欧元腿的日均 vs `M.<CCY>.EUR.SP00.A`」重算，
得到 **max 3.18e−14** —— **与声称的 3.2e−14 严丝合缝**，说明它确实跑过这个对账，
只是**写成了「本模块重算值」**，而本模块输出的 JPY/BRL 两列是美元交叉，不是欧元腿。
两者之差恰恰就是它自己在口径坑 3 讲的 Jensen 间隙。

事实本身成立（ECB 官方「月均」= 当月发布日算术平均，这正是本模块的假设），
没有任何数值因此出错；但这段是模块的**证据链**，照字面复现会得到假警报。

**修复指令**：把那句改成明确限定到欧元腿，例如：

> 与 ECB 自己发布的月频序列 `M.<CCY>.EUR.SP00.A` 对账，验证「月均 = 当月所有发布日的
> 算术平均」就是 ECB 自己的定义。注意对得上的是**各币种对欧元的原始腿**
> （USD/EUR、JPY/EUR、BRL/EUR 的日均），2018-11 至 2019-03 共 15 个月，
> 相对差 ≤ 3.2e-14（纯浮点噪声）。**本模块输出的美元交叉列不能这样对**
> —— ECB 不发布交叉的月频序列，拿两条月频相除会引入口径坑 3 的 Jensen 间隙
> （实测可达 1.75e-04），那是方法差异，不是误差。

  （2011-09 是欧债危机 + 瑞郎设限那波，属另一次波动事件）。清单补全后这句话就不成立了。

### 问题 5 — minor：`BASE_MONTH` 在两个文件里各写了一遍，没有互校

`fetch/fx.py:165 BASE_MONTH='2019-01'` 与 `build/notional.py:85 BASE_MONTH='2019-01'`
是两个独立字面量，`notional.py` 不 import `fetch.fx`。
fx.py 的 docstring 甚至在示例里写了 `# = fetch.fx.BASE_MONTH`，说明作者知道这层耦合，
但只用注释维系。改动其中一个而忘了另一个，后果是**定基链取了一个基期、fx 表锁了
另一个基期**，而两边各自都能跑通、都不报错 —— 又一个「用错了不会报错」的口径坑。
