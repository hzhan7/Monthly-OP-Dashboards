## 发现的虚报与错误

数据层零错误。以下问题全在叙述层，但 **E1 会直接导致实现阶段画错线**。

### E1【中等偏重 · 事实错误 · 会直接影响实现】Cboe Canada **并没有**在 2026-08-02 完成收购

原报告「口径坑 10」写：

> 2026-04-22 宣布收购 **Cboe Canada + Cboe Australia**，2026-08-02 **已完成**
> —— Cboe Canada 是加拿大另一家上市场所，并表后"TMX 加拿大现货成交"的分母会跳变，需要在该月画结构性断点。

**这是错的。** 我查 TMX 自己的新闻稿 feed（2026 年全量）：

```
08/02/2026 | TMX Group Completes Acquisition of Cboe **Australia**      <- 只有澳洲
07/30/2026 | TMX Group and MEMX Announce Strategic Combination ...
04/22/2026 | TMX Group Announces Agreement to Acquire Cboe Australia and Cboe Canada
```

且 Q2/26 MD&A 第 52–55 行原文明确：

> "The purchase of each business is subject to respective regulatory approvals and customary
> closing conditions in Australia and Canada. The two components of this acquisition, Cboe
> Australia and Cboe Canada, are **expected to close separately**, each after required approvals
> have been obtained. We expect Cboe Australia to close in the third quarter of 2026."

即：**两家分别交割；已完成的只有 Cboe Australia；Cboe Canada 尚未完成，MD&A 没给日期。**

**为什么这条要紧**：原报告推荐的动作正是「在该月画结构性断点」。
但 Cboe Australia **完全不碰加拿大现货成交量**，
按原报告照做会在 `2026-08` 给 TMX 的加拿大现货曲线打上一个**根本不存在的断点**，
而真正该打断点的那个月（Cboe Canada 交割月）会被漏掉。

### E2【中等 · 事实错误】「2022-05 及更早的 PDF 里表格整块丢失」不成立

## 给实现阶段的具体警告

按会造成的损害排序。W1–W3 是原报告**没写**的，我自己踩到或实测出来的。

### W1【必须】feed 不带 User-Agent 会 403 —— 原报告说的「纯 urllib 200」不准确

原报告「源 2」写：「抓取方式：**纯 `urllib.request` 200，`curl` 也 200**。实测确认。」
**我实测：默认 UA 一律 403。**

```
urllib 默认 UA (Python-urllib/3.x)  -> HTTP 403
curl   默认 UA (curl/8.x)           -> HTTP 403
urllib/curl + 桌面 Chrome UA        -> 200 application/json
```

结论不变（不需要 curl_cffi、不需要浏览器、cron 可跑），但**必须显式设 UA**。
照字面抄「纯 urllib」写出来的 `fetch/tmx.py` 会在第一次 cron 运行时直接 403 挂掉。
注意 `m-x.ca` 那边**确实**裸 urllib 就 200 —— 两条源的要求不一样，别一刀切。

### W2【必须 · 静默出错】月度表和「Daily Averages」在**同一张 `<table>` 里**，行标签重复

原报告口径坑 15 只警告了「YTD 表和月度表长得一样」。但还有一层更阴的：
**每张月度表的下半部分紧跟一个 `Daily Averages` 子块，`Volume` / `Value` / `Transactions`
三个行标签在同一张表里各出现两次。**

我第一版解析器就栽在这里，且**不报错**：

```
2026-06 all/transactions 被解析成 1,540,000   （其实这是日均笔数）
正确值应为                    33,879,991     （当月总笔数）
```

差 22 倍，但两个数看上去都"合理"，图上不会立刻露馅。
⇒ 解析时必须在遇到 `Daily Averages` 行标签处**停止本表的取数**（或改用「同名行只取第一次出现」）。
这条比原报告列的多数口径坑更危险，因为它静默且结果貌似合理。

### W3【必须】小节标题不能用正则抽 —— 59 期里有 6 期的标题嵌在 `<div role="heading">` 内层

原报告口径坑 3 给的解法（先 squash 空白再比）**必要但不充分**。
在 **2022-03 / 2022-04 / 2022-07 / 2022-08 / 2022-10 / 2023-06** 这 6 期里，
`All TMX Equities Marketplaces` 的标题长这样：

```html
<div class="q4default"><p>…正文…</p>
  <div class="wcag-arialevel-3" role="heading" aria-level="3">
    <b><u>All TMX Equities Marketplaces</u></b><b>&nbsp;*</b>
  </div>
  …
```

标题 div **嵌在** `q4default` div 内层。任何 `<div[^>]*>(.*?)</div>` 式的正则非贪婪匹配
都会从外层 div 起匹到内层的 `</div>`，把标题连同正文一起吞掉 → 该期 `All TMX` 小节**整段丢失**。
我第一版正则解析器就是这样丢了这 6 期。
⇒ **必须用真 HTML parser（bs4/lxml，本机 bs4 4.15.0 + lxml 均已装）按文档顺序遍历，不要用正则。**
换成 bs4 后：59/59 期全部小节齐全，未归属表格 0 张。

同时确认原报告口径坑 3 描述的现象**是真的**，2022-06 原文逐字如此：
```
'TSX Venture Ex\n  \n  \n    change\n  \n  *'
```
所以 squash 也照样要做 —— 两条都要，不是二选一。

### W4【必须】`trading_days_*` 是**推出来的**，不是官方直接给的，且会除零

原报告字段表把 `trading_days_equity` / `trading_days_rates` 与其它字段并列，读起来像官方直接给。
实际上 xlsx **没有交易日数这一列**，只能用 `round(volume / adv)` 反推。两个坑：

* 停用合约会 **0/0**：2026 年的 `BAX` 是 `vol=0, adv=0`，直接除会 `ZeroDivisionError` 或 NaN。
* 必须挑一个**当期成交量足够大的活跃合约**当基准（利率侧建议 `CGB`，股票侧建议 `Equity Options`），
  别用 `GRAND TOTAL` —— 它跨两套日历，实测 2025-09 会推出 **20.499** 这种非整数（见我第 3 节）。

### W5【重要】E1 的直接后果：结构性断点先别画

在 Cboe Canada **实际交割公告出现之前**，不要在任何月份给 TMX 加拿大现货打并表断点。
建议实现时留一个显式的 `BREAKS` 常量并置空，等 feed 里出现
`TMX Group Completes Acquisition of Cboe Canada` 再填。
`Cboe Australia`（已于 2026-08-02 完成）**不影响加拿大现货口径**，不要因为它改任何东西。

### W6【重要】TMX 现货每月会比 CME/Cboe/HKEX 晚一期，别让新鲜度红点误报

实测三家现有序列 `cme.csv` / `cboe.csv` / `hkex.csv` **都已更新到 2026-07**，
而 TMX 的 CTS 现货最新只有 **2026-06**（MX 衍生品倒是有 2026-07）。
总览页有「各家新鲜度红点」，TMX 会在每个月初的头几天**结构性地**显示为落后一期。
⇒ `latest_month()` 必须按 MX / 现货分别返回（原报告写对了），
并且新鲜度判据要对 TMX 现货单独放宽到「次月 15 日」，否则每月误报一次。

### W7【重要】单位不统一：`hkex.csv` 的衍生品是**张**，`cme.csv` 是**千张**

原报告「单一市场垄断对照」池写「`mx_adv_kcontracts` vs HKEX `derivatives_adv_contracts`」，
没提这两列**差 1000 倍**。实测：

```
hkex.csv 2026-07  derivatives_adv_contracts = 1,731,267   （原始张数/日）
cme.csv  2026-07  adv_total_kcontracts      =    26,963   （千张/日）
```

仓库现有的 `build/build_group_exchanges.py` 第 230 行已经在做换算：
`col_of('hkex', 'derivatives_adv_contracts', 1/1000.0)`。
TMX 若按原报告用 `kcontracts`，**与 cme 同制、与 hkex 差 1000 倍**，
放进横截面时必须沿用现有的 `1/1000` 换算，别重复缩放也别漏缩放。

### W8【重要】TMX 现货存的是**月总量**，而横截面所有行都是**每日**口径

`build_group_exchanges.py` 的展示行全是 per-day：
`CME total ADV (k contracts/day)` / `Cboe U.S. options ADV (k contracts/day)` / `HKEX cash ADT (HK$bn/day)`。
原报告提议 `series/tmx.csv` 存**月度总量**（`tmx_all_value_cadbn` 等），
理由是官方印的日均只到 0.1 million —— 这个理由我验证属实：
```
官方印 "490.7 million"    实际 10,796,096,148 / 22 = 490.7316 million
```
所以存总量是对的。但 **TMX 会是全仓唯一一个存总量的家**，build 层必须显式除 `trading_days_equity`。
⇒ 建议在 `build/tmx.py` 里把这条写成注释常量，并加一条断言：
TMX 进横截面的列必须与 cme/cboe/hkex 一样是 `/day` 口径。

### W9【中】字段表补两列，否则复现不出自己的池子数（E5）

`series/tmx.csv` 需补 `mx_adv_cdr_options_kcontracts` 与 `mx_adv_cef_options_kcontracts`，
否则「单股与 ETF 期权」池算出来是 341.1 而不是原报告写的 344.8。
（CEFs Options 是 2025 年后才出现的行，早期档没有 —— 按 section 定位，缺失时给空而非报错。）

### W10【中】m-x.ca 的 xlsx 是活文件，回补与增量会分叉

原报告口径坑 5 写对了，我加一条实测强化证据：`1901`（2019 年 1 月）的
`Last-Modified` 是 **2022-07-23**。历史档被大规模重传过。
⇒ 一次性回补跑出来的 CSV 与三年后重跑的结果**不会逐位相同**，
这不是 bug。建议像 `series/spgi.csv` 那样保留一份原始台账做重述体检基线。

### W11【中】2021-07 及更早的现货缺口：确认无正当线上通道

我复核确认原报告的 D 判定**不是偷懒**：

* 2019-06 / 2020-12 / 2021-07 三期新闻稿 Body **确实只有一句 "Related Document" 加一条 `/resource/en/<id>` 链接，零 `<table>`**；

## 与已有 cme / cboe / hkex 能不能放进同一个竞争池

（这是复核任务额外要求判断的一项。结论：**能，但只有两个池，且现货那条要先做两步换算。**）

先看现有横截面 `build/build_group_exchanges.py` 实际比的是什么：

```python
('cme',  'CME',  'cme.csv',  'adv_total_kcontracts',      'k contracts/day'),
('cboe', 'Cboe', 'cboe.csv', 'adv_us_options_kcontracts', 'k contracts/day'),
('hkex', 'HKEX', 'hkex.csv', 'adt_hkdbn',                 'HK$bn/day'),
```

**全部是「每日」口径**，且合约类统一到「千张/日」。对照 TMX：

| 池 | 可比性 | 判断 |
|---|---|---|
| **衍生品总量 ADV** | ✅ **完全可比** | `mx_adv_kcontracts`（GRAND TOTAL ADV，实测 2026-06 = **1,015.7 千张/日**）与 `cme.adv_total_kcontracts`（2026-07 = 26,963）**同物同单位**，直接放同一张图。量级 MX ≈ CME 的 3.8%，建议指数化或双轴。与 HKEX 的 1,731 千张/日**同数量级**，这一对最漂亮 |
| **利率衍生品** | ✅ **完全可比** | `mx_adv_stir + mx_adv_bond_futures` = 585.5 千张/日 vs `cme.adv_rates_kcontracts` = 12,610.3 → **4.6%**，原报告说的「个位数百分比」准确。单合约 `CGB` vs CME 10Y Note 是最干净的一对一 |
| **单股/ETF 期权** | ⚠ 可比但不是竞争 | 单位一致（千张/日，对 `cboe.adv_multilist_options_kcontracts`），但 **MX 是加拿大盘、Cboe 是美国盘，两者不争同一批订单流**。只能标成「同业务形态规模对照」，图注必须写明，否则会被误读成市占率此消彼长 |
| **现货** | ⚠ **可比，但要先做两步换算** | 见下 |
| **股指衍生品** | ⚠ 口径不对齐 | `mx_adv_index_futures` 是**纯期货**（SXO/SXJ/SXV 实测恒为 0），`cboe.adv_index_options_kcontracts` 是**纯期权**。原报告已警告，我确认属实。同图必须加注，否则是错的 |
| **北美期权（BOX）** | ❌ **不可比** | TMX 只有季度，池里其余三家都是月度。**TMX 在这个池必须缺席**，别为了凑齐而把季度数插值成月度 |
| **FX / 能源 / 加密** | ❌ | USX 日均 0.568 千张 = 噪声；能源与加密无披露 |

**现货那条要注意的两步换算**（原报告方向对，但没说清它是全仓唯一的例外）：

1. **周期换算**：TMX 存的是**月度总量**，其余三家存的都是**日均**。必须除 `trading_days_equity`。
   实测 2026-06：`478,909,112,683 / 22 = C$21.77 bn/日`、`15,568,012,598 / 22 = 0.708 bn 股/日`。
2. **币种/口径换算**：TMX 是 **C$**、HKEX 是 **HK$**、Cboe 现货给的是**股数**不是金额。
   所以横截面**必须指数化**，绝不能把 C$21.8bn 和 HK$115.8bn 画在同一个绝对值轴上。
   原报告主张「金额与股数两个都存」是对的 —— 因为 Cboe 只给股数、HKEX 只给金额，缺任一列就有一家对不上。
